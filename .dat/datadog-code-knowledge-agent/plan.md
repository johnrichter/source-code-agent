## 2. The code chunker (net-new component 1 of 2)

### Problem
Markdown splits cleanly on headings; code does not. Splitting code by line-count or regex produces chunks that cut through function bodies, orphan signatures from bodies, and bury the identifying symbol name — destroying both retrieval relevance and citation usefulness.

### Approach — AST-aware chunking via tree-sitter
- **One chunk ≈ one named symbol** (function / method / class / interface / module-level const block), with its leading doc-comment/decorator attached.
- **Tree-sitter** per language for the boundary detection. The workspace already uses tree-sitter AST parsing via the `smart-explore` skill — that is the reusable basis, not a from-scratch parser.
- **Oversized symbols** (giant functions) split on inner block boundaries with a back-reference header (`// in func X (cont.)`), mirroring the docs chunker's section-continuation handling.
- **Carry a symbol header into the chunk text** so BM25 + embeddings both see `package/module · ClassName.methodName · kind` — this is what makes symbol queries land.
- **Non-code files** (README, package manifests, YAML config, `.proto`) chunk with the existing prose/heading splitter — they answer "how do I configure X" questions and should not be dropped.
- **Test files excluded by default (v1).** They document real usage but roughly double corpus size and churn hardest on refresh; `kind=test` is reserved to re-enable on eval evidence (§10.3).

### Citable text vs. indexable text (the citation guarantee on code)
The forwardable guarantee is that `cited_text` is an **exact substring of the source file**. Two code-specific hazards threaten it; the chunker defends against both:
- **Synthetic symbol header.** We prepend `package/module · ClassName.methodName · kind` so BM25 + embeddings see the symbol — but that header is **not in the source file**. So the chunk carries two fields: `IndexText` (header + body, used ONLY for BM25/embeddings) and `Text` (verbatim source only, the ONLY thing `cited_text` may match). Generation cites `Text`; the header never leaks into a citation. **S0 PROVED this split is mandatory:** when the header was in the citable `Text` (spike corpus B), the generator preferentially cited the header → **0/13 real-source-file integrity** behind a *false* 13/13 engine-verified — a silent forwardability failure. (S0 also found the header gave **no recall lift**: body-only already hit 100% recall — so the header is an optional retrieval tweak, but if used the split is non-negotiable.)
- **Whitespace/formatting.** Already solved by the reused engine: `agent/answer.go verifyCitation` applies **identical whitespace normalization (`normWS`) to both sides**. S0 confirmed code citation-integrity = 100% (real-file) on the body-only config — no whitespace regression.
- **const/var blocks are first-class chunks.** S0's first chunker emitted only func/method/class/type and **silently dropped all const/var blocks** (`ddtrace/ext` is pure constants → 0 chunks). These hold defaults/env-var names — exactly the §6 version-delta surface. P0 must chunk const/var blocks (py ALL_CAPS module assignments; go `const_declaration`/`var_declaration`).

### Per-language scope for the spike
S0 covers **Python** (`dd-trace-py`) and **Go** (`dd-trace-go`) only — two languages, two mature tree-sitter grammars, two already-cloned repos. Each additional language in later phases is an incremental grammar + a handful of node-type mappings, not new architecture.

### Chunk metadata (generalized `resolve.Chunk` for code)
Replace the docs site/selector fields with code fields:
```
Repo        string   `json:"repo"`            // dd-trace-py
Language    string   `json:"language"`        // python
FilePath    string   `json:"file_path"`       // ddtrace/propagation/http.py
Symbol      string   `json:"symbol,omitempty"`// HTTPPropagator.extract
SymbolKind  string   `json:"symbol_kind"`     // func|method|class|module|config|readme
Package     string   `json:"package,omitempty"`
Component   string   `json:"component,omitempty"` // taxonomy overlay (§3): propagation, sampling, ...
StartLine   int      `json:"start_line"`
EndLine     int      `json:"end_line"`
IntroducedIn string  `json:"introduced_in,omitempty"` // first major.minor this chunk's text appeared (§6, idea D)
LastSeenIn   string  `json:"last_seen_in,omitempty"`  // last major.minor it was unchanged in; empty = current
CommitSHA   string   `json:"commit_sha"`      // capture SHA (tag this chunk's text was captured at). Citation SHA for interval/unversioned queries; a fully-specified version re-resolves the permalink+cited_text via git show at the asker's exact tag (§6 hybrid → no line-drift)
URL         string   `json:"url"`             // GitHub permalink @ SHA#Lx-Ly
ContentHash string   `json:"content_hash"`
Visibility  string   `json:"visibility"`      // public|internal — gates forwardability (§5). public repos = customer-shareable; internal (a restricted source, parts of agent monorepo) = restricted
Text        string   `json:"text"`            // CITABLE: verbatim source only — cited_text must substring-match this; NEVER includes the synthetic symbol header
IndexText   string   `json:"index_text"`      // INDEXABLE: symbol header + Text, for BM25/embeddings only — NOT citable (the header is not in the source file)
```
`URL` is the citation: `https://github.com/DataDog/<repo>/blob/<sha>/<path>#L<start>-L<end>` — clickable, pinned, forwardable.

## 3. Taxonomy: language → repo → component → symbol

Mirror the docs `taxonomy.json` overlay pattern (curated, glob-driven, longest-prefix-wins, confidence-queued), with code axes:

- **language** (python, go, java, …) — derived reliably from repo + file extension.
- **repo** (dd-trace-py, browser-sdk, datadog-agent, …) — derived from clone dir.
- **component** (the curated overlay, the actual work): `propagation`, `sampling`, `instrumentation/<integration>`, `profiling`, `appsec`, `telemetry`, `transport`, `config`. Path globs propose; hand-correct the long tail. This is the analog of the docs `suite→product` curation and is what powers cross-repo "how does sampling work everywhere" questions.
- **kind** ∈ `{func, method, class, module, integration, config, readme, test, internal, generated, vendored}` — lets retrieval treat config/README as first-class, **exclude `test` by default (v1)**, down-weight `generated`/`vendored`, and **flag `internal`** (private/underscore-prefixed, not part of the public API). `internal` symbols stay retrievable, but any answer built on one is marked an **unofficial workaround** (§5) — this is the symbol-level analog of the repo-level `visibility` flag.

**Shared-core libraries (libdatadog) — a distinct slice, not a tracer.** `libdatadog` (Rust/C; `language=rust`, C headers) is the shared core that the tracers/profilers **vendor**, not a customer-installed tracer. Tax it on its own component axis — `profiling`, `crashtracker`, `data-pipeline`/`ddsketch`, `telemetry`, `remote-config`/`dynamic-config`, `appsec` (libddwaf surface), `ffi`/`bindings` — so a "where is this implemented in the shared core" question resolves to libdatadog while the per-tracer wrapper still answers "how does language X call it". Its versioning is **derived from tracer pins** (§6), not measured. (`dd-trace-go` is the exception that does **not** vendor libdatadog — pure-Go + `datadog-agent/pkg/*` + `go-libddwaf`.)

Cross-repo / cross-language questions are the design center (analog of the docs cross-suite case): **retrieval-side fan-out per repo/language → merge → single generation call.** Reuse `SearchFanout`. **libdatadog is the cross-cutting hub of this fan-out:** "how does profiling/crashtracking/telemetry work" legitimately fans out to libdatadog + each tracer's binding, and the §6 version mapping is what lets that answer name the right libdatadog version per tracer version.

## 4. Retrieval tuning for code

Keep the hybrid BM25+vector+RRF+rerank core; retune, don't rebuild:
- **~~Weight BM25 up.~~ MEASURED & REFUTED (P2, 2026-06-23):** the hypothesis was that exact identifier match dominates for code, so BM25 should outweigh vectors. The eval sweep disproved it on natural-language code questions — bm25×2/×3 *lowered* recall@4 (8/10 vs equal-hybrid 9–10/10) and worsened mean rank (2.20 vs 1.50–1.60); nomic embeddings already match NL→code well, and over-weighting BM25 adds token noise. **Default is equal-weight hybrid (1.0/1.0)**, which keeps BM25 as insurance for bare-identifier lookups (vector-only alone is weaker there) without letting it dominate. The arms are independently weightable (`Index.SetWeights`) so this is re-tunable per the gate as the corpus grows.
- **Optional symbol index** — a direct `symbol → chunk` map for "show me `HTTPPropagator.extract`" lookups, short-circuiting before hybrid search. **P2 decision: NOT built** — all per-language symbol lookups already retrieve at rank 1, so it's YAGNI. Revisit only if symbol queries underperform on a larger corpus.
- **Embeddings:** start with the same local `nomic-embed-text` (offline, free) and **measure** in S0. If code recall is poor, evaluate a code-tuned embedding model — but do not add a dependency before the eval forces it (same discipline as docs §5 vector-store decision).
- **Reranker** ports verbatim and matters more at code scale.

## 5. Generation (unchanged engine)

Reuse the shipped path verbatim: cached grounding prefix + per-chunk citable `document` blocks + Citations API + **`cited_text` verification** + no-truncation continuation loop.

**Code is structurally simpler than docs here — lean into it.** Docs needed a serve-time `ResolveText` transform (region placeholders) between corpus and citation; **code has none.** Chunks are verbatim source — there is nothing to resolve between the indexed text and the citation, so a code citation is *more* trustworthy than a docs citation: the bytes you cite are the bytes in the repo at the SHA. (The only query-time resolution is the §6 hybrid pinning the permalink SHA to the answered version — and that re-verifies `cited_text` against that exact SHA.)

Code-specific additions:
- Grounding prompt: "answer strictly from the cited source; quote the exact symbol; name the repo, language, file, and line range; if behavior differs across tracers, say so per-language."
- Output a `branches`-analog field: `covers: [{repo, language, symbol}]` so a cross-tracer answer is explicit about which implementation each claim comes from.
- **Cite `Text`, never `IndexText`** (§2) — the synthetic symbol header is for retrieval only and must never appear in a citation.
- **`cited_text` verification normalizes whitespace identically on both sides** (§2) — code's tabs/trailing-whitespace/CRLF must not cause spurious verification failures.
- **Visibility gating (§5 / privacy header):** an answer is **customer-forwardable only when every citation's `visibility=public`.** If any citation is from a restricted repository, the answer is **restricted** and labeled as such.
- **Unofficial-workaround rule (customer-reliable by default; unsupported workarounds allowed):** default to public/supported API (public repos, non-`internal` kinds). When the only viable solution requires `internal`/`generated`/`vendored` symbols or a restricted repository, the agent **must** prefix that part of the answer with `[UNOFFICIAL — not a supported API; may break without notice; specialist use only]` and never present it as a supported path. Make the hack explicit and obvious, never silent.
- **Hard rule (carry over):** the answer is forwardable only when every citation is `verified` true (the `cited_text` substring-matched its source file at the SHA the permalink points to).

## 6. Versioning — FIRST-CLASS, not deferred (the customer reality)

The docs agent's 8-site resolution machinery does not apply, but **version is the code agent's equivalent axis and it is load-bearing**: this is a field/a specialist tool, "which version are you on?" is the first question on every support thread, — the long tail of old versions is exactly where behavior surprises live. Version is to code what site was to docs: harder (N = hundreds of tags, divergence is *structural* — renamed options, removed integrations, changed defaults), but de-risked by the same economics the docs build measured (**~88% of chunks were byte-identical across sites; adjacent code versions share most code, so content-hash dedup makes real cost ≈ 1× + the diffs**).

**Chosen model: D (per-symbol version intervals) at major.minor granularity, bounded by install data (E), with B + C as complements** (decided with the user 2026-06-22). major.minor — not major — because defaults and option renames land on *minors*.

1. **Version intervals (D) — the primary index.** Each chunk carries `introduced_in → last_seen_in` (major.minor); a query for version X filters to chunks whose interval covers X. One logical corpus, interval predicate at query time. Built by walking the repo's tags and diffing symbol-by-symbol.
2. **Bound the version set, and treat that bound as the cost lever.** **Committed artifact: `version-sets.json`** (this dir) — `repo → { lines: [major.minor…], visibility, source, provenance_date, caveats }`. It is the reviewable, diffable source of truth that the `reselect-versions` mode (§P7) regenerates. The empirical findings below **materialize into it**, not into prose. Do **not** backfill every minor ever shipped. Take each repository's released tags and index backward from the latest, until the list is exhausted or the per-repo cap is reached.
   - **The version set is bounded by usage data, and that input is unavailable.** A public consumer cannot reproduce it: the distribution of deployed versions is only visible from inside the organization that runs the service. Substitute a public rule instead — take each repository's released tags, and index backward from the latest until the tag list is exhausted or a chosen cap is reached.
   - **Supported-majors floor from the published per-tracer support and end-of-life policy.** That policy is public, so this floor survives outside the vendor. Language labels need normalization before use.
   - **Serverless layer versions stay unresolved.** No public source reports which layer version is in use, and the unavailable source records the function's own version rather than the layer's. The fallback for that slice is to index the default branch, overlay the changelog, and resolve on demand.
   - **Shared-core libraries take a derived version set, not a measured one.** The shared Rust and C core is vendored by each tracer and profiler rather than installed on its own, so no usage source reports its version. Each tracer release pins one core version, and that pin is public, so the core's version set is derived from the tracer's. This is the 1:1 mappability rule.
3. **Changelog overlay (B) — complement.** Index each repo's `CHANGELOG`/release-notes/migration-guides as first-class prose chunks. Human-authored source of truth for "what changed in your version"; cheap; bridges deltas between indexed minors.
4. **On-demand `git show` (C) — sub-minor resolver.** For patch-level exactness below indexed granularity: retrieve on the nearest indexed minor (recall), then `git show <tag>:<file>` the clone to confirm/cite the customer's precise line (precision). C alone fails as a primary index (latest-vocabulary retrieval misses renamed/removed old symbols); as a resolver it's exact.

**Cost of D @ major.minor (front-loaded, not linear):**
- **Storage ≈ 1.31× latest-only (MEASURED in S0), *not* N×** — content-hash dedup collapses the unchanged majority as predicted. S0 chunked py (8 minors v3.12→v3.19) and go (7 minors, stable-layout window v1.67→v1.73) → **both 1.31×**, adjacent-minor churn 5.8% (py) / 9.8% (go). Real driver = cumulative churn, not version count. Confidence **upgraded medium-low → medium-high**; the ~30-line/repo cap projects comfortably under the original 3–5× ceiling. (Caveat: the multiplier grows sub-linearly with more minors; re-measure at the cap during Pv. The go full-8 window showed 5.12× — an **artifact** of the v1.74 file relocation leaving the scoped path, see the symbol-identity bullet below, not real storage churn.)
- **One-time historical backfill is the real cost** — AST-parse + diff every indexed minor (hours for the full tracer set). The install-data bound (step 2) is what keeps it tractable.
- **Ongoing refresh is cheap** — a new release diffs against the prior tag only; add changed symbols, close/extend intervals; never re-walk history.
- **Retrieval runtime unchanged** — interval filter is as cheap as a branch filter.
- **Hard engineering bit: symbol identity across refactors** (rename/move = "changed" vs "removed+introduced") — **S0 confirmed this is THE binding hard problem.** dd-trace-go relocated ~24 `ddtrace/tracer` files into internal packages at v1.74; a path-anchored, qualified-name-keyed interval index mis-counted the *moves* as mass remove+introduce (the spurious 5.12× / 191-chunk outlier). **Mandate: key symbol identity REPO-WIDE (qualified-name + body-similarity re-link), never on a frozen path.** **Accuracy-first bias (the whole point of D): when continuity is uncertain, treat it as removed+introduced, NOT changed.** That under-claims interval span — "confirmed in 2.6–2.8" rather than falsely "2.0–2.8" — the safe direction for a forwardable tool. But S0 shows pure-conservative + path-scoped is *too* pessimistic across big refactors, so the **body-similarity re-link is required (not optional)** to avoid mass false-removals on relocation; default conservative only on genuine doubt.
- **LFS budget**: 3–5× a (larger-than-docs) code corpus → confirm quota before the bulk backfill (open decision §10.7).

**Query behavior (D for recall, C for citation precision — the hybrid):** `-version 2.8.3` → D's interval filter selects chunks whose interval covers 2.8 (drives recall + the behavioral answer + delta-flagging) → **the citation permalink + `cited_text` are then pinned to a SHA matching the answered version:** for a fully-specified version, resolve via `git show <nearest-tag-for-2.8.3>:<path>` (C), locate the symbol, emit the permalink and verify `cited_text` at *that* SHA; for an interval-only or unversioned query, cite the capture SHA of the covering minor (or latest). **This eliminates line-number drift** — the permalink's SHA is always the SHA the citation was verified against, never a different one (the line-drift hazard a naive D would introduce). Bridge deltas via the changelog overlay; flag when the exact patch ≠ indexed minor. C requires the repo clone present at query time (already required); note this for the detached Slack-responder face.

**Rejected:** `main`-only (wrong — users are mostly *not* on latest); major-only branches.

## 7. Eval (the trust gate)

Reuse the docs two-gate, deterministic, no-LLM-judge structure:
- **Offline retrieval gate** (no gateway, fast, never flakes): is the golden source file in the top-N pool for the question? Owns precision/recall of the chunker + retrieval.
- **Full gate**: citation-integrity (every `cited_text` matches its file at the SHA) + behavioral checks + refusals.
- **Golden cases** stratified across: per-language symbol lookups, component questions (propagation/sampling/instrumentation), **cross-repo** ("how does context propagation differ between py and go"), config/README questions, **version cases** (a question against an old major where behavior differs from latest — assert the answer reflects the named version + flags the delta), and **refusals** (a symbol that doesn't exist → no citation, clean refusal).
- **Assertion style (code-specific, anti-flake — code goldens rot faster than docs goldens):** assert on a discriminating **identifier** — a const name, a function-signature fragment, a changed default **value** — not on `cite_url_contains` a file path (paths move every refactor; def/usage/re-export all legitimately answer). Make version-case delta-flagging **deterministic without an LLM judge**: `must_contain` a known-changed value (e.g. old default `2.0` vs new `4.0`) **and** a literal delta marker the grounding prompt is required to emit (e.g. `changed in`).
- Citation-integrity = true on every answer is the hard pass condition.

2. Stand up a throwaway chunker using tree-sitter Python + Go grammars; emit symbol-aligned chunks with `{repo, language, file_path, symbol, symbol_kind, start_line, end_line, sha, text}`.
3. Reuse the existing `ka` embed + retrieve + generate path against those chunks (point it at a scratch corpus; no site flags).
4. Hand-write ~15 golden questions spanning: a Python symbol lookup, a Go symbol lookup, a propagation question, a sampling question, an integration/config question, a cross-language compare, and 2 refusals.
5. Score against the **fixed go/no-go bar (set before running): golden-file-in-top-N recall ≥ 85%, citation-integrity = 100%, version-case delta-flag = 100%.** Citation-integrity here specifically exercises the two code hazards: (a) `cited_text` substring-matches the source after *identical* whitespace normalization both sides; (b) the synthetic symbol header lives only in `IndexText`, never in the citable `Text`, so it never leaks into a citation (§2, §5).
6. **Measure the version-interval cost (§6):** chunk py+go at ~5–10 successive major.minor tags each, content-hash the chunks, and compute the **churn/dedup ratio** (unique chunks ÷ latest-only chunks). This converts the "3–5×, medium-low confidence" storage estimate into a hard projection before any historical backfill is committed.
7. **Decide against the bar:** at/above → proceed to D0; below recall → swap the embedding model / add a symbol index before D0; below citation-integrity → fix whitespace normalization or the `IndexText`/`Text` split first (it's the core guarantee, before anything else); confirm the interval-model storage projection is within LFS budget.

Spike code lives in `scratchpad/` or a throwaway dir — it is not the production module (D0 starts the real module by copying `ddocs`).

## 13. Build execution: tiering & orchestration

**The build is heterogeneous — do not set one model/effort tier for all of it.** Reasoning concentrates in ~30% of the phases; the rest is engine-port + mechanical + throughput. Match the builder tier to each phase's *binding constraint* (reasoning-bound vs. correctness-bound vs. throughput-bound).

> **Two distinct "models" — don't conflate:** the **product's** models are already locked (a model gateway `claude-opus-4-8` for generation/rerank where citation-faithfulness is load-bearing; local ollama `nomic-embed-text` for the embedding bulk — §11). This section is about the **builder agent** writing the Go/chunker/eval. Build = local compute, ~zero API tokens until query/eval, so the cost is reasoning time.

### Per-phase builder tier

| Phase | Bottleneck | Builder tier |
|---|---|---|
| **S0 spike** (chunker prototype, what-to-measure, go/no-go interpretation) | Reasoning/judgment | **opus · high · extended-thinking** |
| **D0 module seed** (copy ddocs→ddcode, strip site-resolution, tests green) | Mechanical correctness | sonnet · medium |
| **P0 chunker** (AST mappings, IndexText/CiteText split, oversized-symbol logic) | Reasoning + engineering | **opus · high · extended-thinking** (net-new #1, citation-critical) |
| **P1 taxonomy** (glob rules + hand-correct long tail) | Curation judgment | opus · medium (review-queue style) |
| **P2 retrieval retune** (BM25 weighting, embedding-model call) | Empirical measurement | sonnet · medium; bump for the embedding-model decision |
| **P3 eval suite** (non-rotting goldens, deterministic delta checks) | Adversarial design | **opus · high** for design; the run is mechanical |
| **Pv version intervals** (symbol identity, D+C hybrid, conservative bias) | Hardest reasoning in the plan | **opus · high · extended-thinking** (net-new #2, the larger) |
| **P4 faces** (MCP tool, subagent `.md`, flags) | Mechanical | sonnet · low/medium |
| **P5 incremental refresh** (content-hash, orphan prune, interval extend) | Correctness | sonnet · medium |
| **P6a/b/c scale-out** (clone + grammar + globs per repo) | Throughput | sonnet · medium; P6c (monorepo allowlist + visibility) a notch up |
| **P7 refresh skill** (rebuild/refresh/reselect modes) | Plumbing + orchestration | sonnet/opus · medium |

`xhigh`/`max` thinking: reserve for Pv's symbol-identity correctness and P0's citation-guarantee edge cases **only if those specifically prove stubborn** — never as a blanket default.

### Execution architecture (matters more than per-call tier)
- **Orchestrate, don't monolith.** A high-tier architect (opus · high) holds the plan, designs the hard components, makes the go/no-go calls, and reviews — staying in the loop across phases. Right-sized workers (sonnet · medium) do the mechanical surgery.
- **Fan out the parallelizable phases.** P6 scale-out (N repos, homogeneous), per-language P0 grammars, and P3 golden-case generation are textbook subagent/Workflow fan-out — independent units, one verification gate at the end. Worth an explicit Workflow when we reach them.
- **The gates are the quality lever, not the effort dial.** The S0 numeric bar + the deterministic two-gate eval + per-citation integrity (§7) are what guarantee correctness — and they are exactly what *lets* lower-tier workers run the mechanical phases safely, because a regression is caught by the gate, not by hoping a bigger model didn't slip. Cranking effort everywhere is not a substitute for the gate and buys nothing on port/plumbing work.
